# C# scripting for Cocos Creator

Write Cocos Creator 3.8 scripts in **C#**. You call the **Cocos API directly**, with the same class and method names as in TypeScript, so the Cocos documentation applies 1:1. There is no Unity-style API layer: C# is just another language for the same engine.

Each `Player.cs` under `assets/` is compiled with Roslyn (the real C# compiler) and written as `Player.ts` next to it. Cocos then compiles that file like any other script.

```
assets/Scripts/Player.cs  --(Roslyn + Cocos bindings)-->  assets/Scripts/Player.ts  --(Cocos)-->  game
```

## Setup

1. Install the **.NET SDK 9** or newer (https://dotnet.microsoft.com/download).
2. Enable the `csharp` extension. The first time it needs to, it builds its transpiler with `dotnet build`; this takes about 10 seconds. The Console shows "[C#] Transpiler built."
3. Optional, for IntelliSense: **VS Code** with **C# Dev Kit**, **Rider** or **Visual Studio**.

## Quick start

1. Choose **Create → C# Script** (or **C# Class**) and type the name, for example `Player`:
   - in the **Project browser**, the name comes first: a placeholder waits for it, and `Player.cs` is created with `class Player` only when you press Enter (Esc creates nothing);
   - in Cocos' **Assets panel**, `NewComponent.cs` is created and put straight into rename mode; renamed before you edit it, its class follows the file name.
2. If nothing happened to the name yet, rename the file: the class follows until you edit the script.
3. Choose **Extension → C# → Open C# Project**. This writes `CocosGame.csproj` at the project root and opens the project in VS Code, or in your `.csproj` editor if VS Code isn't installed.
4. Edit the script and save. `Player.ts` appears next to it, marked `// <auto-generated>`.
5. Add the **Player** component to a node, as with any script, and press Play.
6. C# errors appear in the Cocos **Console** as `assets/Scripts/Player.cs(12,9): error CS0103: ...`. While a file has errors, its previous `.ts` is kept.

```csharp
[Menu("Samples/Rotator")]
public class Rotator : Component
{
    [Tooltip("Degrees per second")]
    public double speed = 90;     // public: saved and shown in the Inspector

    public Node target;

    public Node[] extras;

    private double _angle;        // private: not saved

    protected override void start()
    {
        if (target == null) target = node;
    }

    protected override void update(double dt)
    {
        _angle += speed * dt;
        target.setRotationFromEuler(0, _angle, 0);
    }
}
```

becomes

```ts
// <auto-generated> from Rotator.cs by the C# extension. Edit the .cs file: this file is overwritten.
import { Component, Node, _decorator } from 'cc';
const { ccclass, menu, property } = _decorator;

@ccclass('Rotator')
@menu('Samples/Rotator')
export class Rotator extends Component {
    @property({ tooltip: 'Degrees per second' })
    speed: number = 90;
    @property(Node)
    target: Node = null;
    @property([Node])
    extras: Node[] = [];
    private _angle: number = 0;
    protected start(): void {
        if (this.target == null) {
            this.target = this.node;
        }
    }
    protected update(dt: number): void {
        this._angle += this.speed * dt;
        this.target.setRotationFromEuler(0, this._angle, 0);
    }
}
```

## The Cocos API in C#

Every script gets these global usings: `System`, `System.Collections.Generic`, `System.Linq`, `System.Threading.Tasks`, plus `using static ProjectExports` for [your TypeScript](#using-your-typescript-from-c-ts-interop). Extensions have their own namespaces: see [Namespaces](#namespaces).

| TypeScript | C# |
|---|---|
| `import { Node, Vec3 } from 'cc'` | `using cc;` at the top of the file, like `using UnityEngine;`. New scripts start with it. |
| `director`, `input`, `instantiate(...)`, `tween(...)`, `find(...)`, `log(...)` | The same names, after `using static cc.Globals;` (new scripts start with it too). |
| `number` | `double`. `int` and `float` also work everywhere. |
| `this.node`, `this.getComponent(Sprite)` | `node`, `getComponent<Sprite>()`. Same for `addComponent<T>()`, `getComponentsInChildren<T>()`... |
| `resources.load('x', Prefab, cb)` | `resources.load<Prefab>("x", (err, prefab) => ...)` |
| `Node.EventType.TOUCH_START`, `Input.EventType.KEY_DOWN`, `KeyCode.SPACE` | The same. |
| `node.on(type, this.onTouch, this)` | `node.on(type, onTouch, this)`. The method is bound once, so `off` finds it again. |
| `label.string = 'x'` | `label.@string = "x"`. `string` is a C# keyword, hence the `@`. |
| `start()`, `update(dt)`, `onLoad()`... | `protected override void start()`, `update(double dt)`... The `override` keyword is optional. |
| `@ccclass('Name')` | Nothing: components and `[Serializable]` classes get it automatically. `[ClassName("Other")]` sets another name. |
| `@property` | Nothing for public fields; see **What is saved** below. |
| `@menu`, `@executeInEditMode`, `@requireComponent(Sprite)`, `@executionOrder(-1)`, `@disallowMultiple`... | `[Menu("...")]`, `[ExecuteInEditMode]`, `[RequireComponent(typeof(Sprite))]`, `[ExecutionOrder(-1)]`, `[DisallowMultiple]`... (see below) |

**Logging.** Cocos' own functions colour the Console line by level: `log("…")` (`cc.log`), `warn("…")` (yellow) and `error("…")` (red). The .NET ones work too: `Console.WriteLine` / `Debug.WriteLine` become `console.log`, `Debug.Assert(cond, msg)` becomes `console.assert`, and `Debug.Fail(msg)` becomes `console.error`. `Console.Error` is not mapped. String interpolation with formats (`$"{x:F2}"`) works in all of them.

**Vector operators** are a C# convenience. Each makes a new value: `a + b`, `a - b`, `-v`, `v * s`, `s * v`, `v / s` on `Vec2`/`Vec3`/`Vec4`, and `q1 * q2` on `Quat`. They become `Vec3.add(new Vec3(), a, b)` and so on. `==` compares references, as in TypeScript; use `a.equals(b)` to compare values.

## Using your TypeScript from C# (TS interop)

C# sees the TypeScript the project already has: the scripts under `assets/` and the runtimes of extensions that mount an asset db (`db://tween-pro`, `db://input-system`, `db://addressables`...), whether the extension is in the project's `extensions/` or in Creator's global folder (`%USERPROFILE%\.CocosCreator\extensions`; the project's copy wins). Use it like the Cocos API; the imports are written for you.

```csharp
// Scripts/TsLib/Health.ts exports: class Health extends Component, enum Team, function formatHp
using Ext.TweenPro;                         // tween-pro (an extension): its namespace

public class Arena : Component
{
    [SerializeField] private Health boss;   // a TS component as a saved reference
    public Team team = Team.Enemy;          // a TS enum, shown as a dropdown

    protected override void start()
    {
        var hp = getComponent<Health>() ?? addComponent<Health>();
        log(formatHp(hp.hp, hp.maxHp));
        Tw.move(node, new Vec3(0, 2, 0), 1).setEase(Ease.OutBack);   // tween-pro
    }
}
```

```ts
// generated
import { Health, Team, formatHp } from './TsLib/Health';
import { Ease, Tw } from 'db://tween-pro/index';
```

**What is visible.** Only exports: classes (components and `@ccclass` data classes too), interfaces, enums, functions and `const`/`let` variables. Type aliases are followed where they are used. `export *` and `export { x } from` barrels are followed; an extension's export is imported from its `index` module when that re-exports it. Generated `.ts` files (C# output) are skipped: C# already sees their `.cs`.

**Names.** See [Namespaces](#namespaces) below: the project's TypeScript needs no `using`, an extension's needs `using Ext.<Package>;`. In the generated file, an import is renamed (`lerp as lerp_ts`, `Input as Input_ts`) when the name is taken there.

**Types.** As for the Cocos API: `number` → `double`, callbacks → `Action`/`Func`, `Promise<T>` → `Task<T>`, methods returning `this` return the class, so fluent calls stay typed. `Iterator`, `IterableIterator`, `Generator` and interfaces shaped like an iterator (only `next()`, `return?()`, `throw?()`, like unity-style's `IteratorLike`) → `IEnumerator` (`IEnumerator<T>` with an element type), `Iterable<T>` → `IEnumerable<T>`, so a [C# iterator](#coroutines-and-iterators-yield) passes where the TypeScript takes one. What has no C# form (mapped types, `Record`, untyped values...) becomes `dynamic`: it compiles and runs, without IntelliSense. String enums are strings in C#, used through their constants (`DamageKind.Ice`).

**Serialization.** TS components, TS `@ccclass` classes and TS enums can be saved fields, like Cocos types: `@property(Health)`, `@property({ type: Enum(Team) })`. A C# component can extend a TS component (`class BossHealth : Health`).

### TypeScript decorators as C# attributes

An exported decorator is also an attribute: `@showIf('mode', 1, 2)` is `[ShowIf("mode", 1, 2)]`. This works for the Odin-like attributes of advanced-inspector, for cocos-playground's `@playGroundField`, and for your own decorators.

```csharp
using Ext.AdvancedInspector;                          // the attributes of advanced-inspector
using Ext.CocosPlayground;                            // [PlayGroundField]
using AI = Ext.AdvancedInspector;                     // for [AI.ReadOnly] (cc has a [ReadOnly] too)

public class Enemy : Component
{
    [Title("Stats", Subtitle = "Health and speed")]   // @title('Stats', { subtitle: '...' })
    [ProgressBar(0, 100, "#e04040")]
    public double hp = 100;                           // @property stays automatic, right above the field

    [ShowIf("isBoss"), AI.ReadOnly]                   // @showIf('isBoss') @readOnly
    public int phase = 1;

    [PlayGroundField(Label = "Headline")]             // @playGroundField({ type: CCString, label: 'Headline' })
    public string headline = "Play now!";

    [Button("Spawn", Size = "large")]                 // @button('Spawn', { size: 'large' })
    public void Spawn() { }
}
```

- **What counts as a decorator.** An exported function or constant that is, or returns, a function shaped like a decorator: `(target, key, descriptor?)` for fields, properties and methods, `(ctor)` for classes. The shape can come from a type alias (`type Decorator = ...`), `PropertyDecorator`, or the function it returns. A constant usable both as `@readOnly` and `@readOnly()` is written bare.
- **Arguments.** The attribute's constructor takes the factory's positional parameters, with their defaults; a rest parameter is `params object[]`. An options object (an interface or `{ ... }` type) becomes named properties in PascalCase: `[Button("Spawn", Size = "large")]`. C# attributes only take constants, `typeof`, enum values and arrays, so:
  - unions, `any` and `unknown` are `object`;
  - `typeof(Color)` becomes `Color`, `typeof(string)` / `typeof(int)` / `typeof(float)` / `typeof(bool)` become `CCString` / `CCInteger` / `CCFloat` / `CCBoolean`, `new[] { typeof(X) }` becomes `[X]`;
  - arrays (`new double[] { 120, 200, 255 }`) become array literals;
  - an argument left out stays out (or `undefined`), so the TypeScript default applies.
- **Order.** Decorators keep the order of the attributes. The automatic `@property` comes last, right above the member; with C#-style attributes (`[Range]`, `[Tooltip]`...), it takes the place of the first one.
- **Decorators that declare the property.** A decorator calling cc `property(...)` itself (like `@playGroundField`) replaces our `@property`, so a field never gets two. When its options have a required `type` and you don't set `Type`, it is filled from the field, as for `@property` (`string` → `CCString`, `Texture2D[]` → `[Texture2D]`, an enum → `Enum(E)`). The field's other C#-style attributes (`[Tooltip]`, `[Range]`, `[Slide]`, `[Multiline]`...) go into its `property` options, since a `Record<string, any>` option can't be written in a C# attribute. A private field with such a decorator is saved and shown, like `[SerializeField]`.
- **Targets and repetition.** `AttributeUsage` follows the decorator: fields and properties, methods (a decorator needing the descriptor is for methods only), or classes. Decorators that add to a list (`@inlineButton`, `@showIf`, `@infoBox`) allow several of themselves.
- **Namespaces.** An attribute lives with its decorator: `Ext.AdvancedInspector.ShowIfAttribute`, used as `[ShowIf]` after `using Ext.AdvancedInspector;`. The C#-style attributes (`[ReadOnly]`, `[Range]`, `[Tooltip]`, `[Min]`, `[Max]`, `[Group]`, `[Type]`, `[Menu]`...) stay in `cc`, so `using cc;` is enough for them. When an extension has one of these names (advanced-inspector's `readOnly`), `[ReadOnly]` next to its using is ambiguous (CS0104): write `[Ext.AdvancedInspector.ReadOnly]`, or add `using AI = Ext.AdvancedInspector;` and write `[AI.ReadOnly]`.
- **Duplicates of csharp's own attributes are left out.** A decorator named like one of csharp's attributes (`[SerializeField]`, `[Tooltip]`, `[Range]`, `[Min]`, `[Multiline]`, `[HideInInspector]`, `[RequireComponent]`, `[ExecuteInEditMode]`, `[Menu]`..., and System's `[Serializable]` / `[NonSerialized]`) that means the same thing to Cocos is not bound as an attribute, so `[Tooltip]` stays csharp's and is never ambiguous. "The same thing" is checked in its code: it uses the cc `_decorator` member the built-in stands for (unity-style's `Tooltip(t)` is `_decorator.tooltip(t)`, its `SerializeField` is `_decorator.property`, its `Min` is `_decorator.rangeMin`), or, for `[NonSerialized]`, it does nothing (no assignment, no call but to its own module's inert functions). Each one is a `duplicate:` line of the report. The others stay: unity-style's `[Header]`, `[Space]`, `[AddComponentMenu]`... (csharp has no such names), and a same-named decorator with another meaning, like advanced-inspector's `readOnly` (its own Inspector metadata, where csharp's `[ReadOnly]` is Cocos' `readonly` option), which stays ambiguous as described below. The decorator function itself stays callable (`Ext.UnityStyle.Exports.Tooltip(...)`). To bind a duplicate anyway, put `/** @csharp keep */` on the decorator.
- **Coverage.** All 32 decorators of advanced-inspector bind with every parameter and option (8 flags such as `[ShowInInspector]`, `[AI.ReadOnly]`; 24 factories such as `[ShowIf]`, `[Button]`, `[BoxGroup]`, `[ValueDropdown]`). The report (`decorator: ...` lines) shows each attribute's signature and anything left out.

**Unity-named messages.** Cocos calls `update`, so `void Update()` in a component is reported as a probable typo (warning CSX2010). Not when a TypeScript base class calls such methods itself:
- a base class that declares the method (the C# one overrides or hides it);
- a base class whose JSDoc has the `@unityMessages` tag, like unity-style's `MonoBehaviour` (it maps `Awake`, `Start`, `Update`, `LateUpdate`, `FixedUpdate`, `OnEnable`, `OnDisable`, `OnDestroy` to the Cocos hooks). The stub gets `[TsUnityMessages]`, and every C# class deriving from it, directly or not, may use those names. Any extension can mark its own base class the same way:

```ts
/**
 * My MonoBehaviour-like base.
 * @unityMessages
 */
@ccclass('my.Behaviour')
export class Behaviour extends Component { /* calls this.Update(dt) from update(dt)... */ }
```

**When it updates.** The stubs (`temp/csharp/TsBindings.g.cs`) are regenerated when a hand-written `.ts` is added, changed, moved or deleted, then the C# recompiles. **Extension → C# → TS Interop...** shows the last run and regenerates on demand; **Regenerate Bindings** regenerates them too. Each run writes `temp/csharp/ts-bindings-report.txt`: what was bound, what became `dynamic`, what was skipped and why, and the clashes. The Console gets one summary line when something changed.

**Excluding files.** In the **TS Interop** window, one pattern per line, matched against `db://assets/Scripts/Foo.ts` and `assets/Scripts/Foo.ts`:
- `**/Editor/**`: any `Editor` folder; `**` crosses folders, `*` stays in one;
- `db://input-system/**`: a whole extension;
- `assets/Legacy`: a path without wildcards is a folder (or a file).

The list is a project setting (`settings/v2/packages/csharp.json`, `tsInterop.exclude`), so it is shared through version control.

**The fallback.** Anything not bound (excluded, skipped, or a script without exports) is still reachable by name, untyped: `dynamic hp = getComponent("Health"); hp.damage(5);`. The names are used as written.

### Namespaces

The same scheme as Unity: the engine is a namespace you import (`using cc;`, like `using UnityEngine;`), packages have their namespace, your code is in the global namespace.

| What | C# namespace | In a script |
|---|---|---|
| Cocos | `cc` (plus `cc.Globals`: `director`, `log`, `tween`...) | `using cc;` and `using static cc.Globals;`. Without them the error says which one is missing. `EventHandler` and `ValueType` exist in both `System` and `cc`: where you use one, write `cc.EventHandler` or add `using EventHandler = cc.EventHandler;`. |
| The C#-style attributes (`[ReadOnly]`, `[Range]`, `[Tooltip]`, `[SerializeField]`...) | `cc` | Nothing. |
| The project's TypeScript (`assets/`) | The global namespace, like your C# classes; functions and variables in `ProjectExports` | Nothing: `EventBus.emit(...)`, `formatHp(...)`. |
| An extension's TypeScript, project or global (`extensions/tween-pro`) | `Ext.<Package>`, the package name in PascalCase: `Ext.TweenPro`, `Ext.InputSystem`, `Ext.AdvancedInspector`, `Ext.CocosPlayground` | `using Ext.TweenPro;` (like `using DG.Tweening;`). Functions and variables: `using static Ext.TweenPro.Exports;`. |

- **Your names win.** A project TypeScript class named like a Cocos one (`Vec3`) hides Cocos' in C#, as a C# class of yours would; `cc.Vec3` still reaches Cocos'. A C# class named like a project TypeScript export hides the TypeScript one (message CSX3010).
- **A class named like its extension** is fine: `using Ext.InputSystem;` then `InputSystem.frame` (the `Ext.` root is there so that a namespace and a class never share a name at the top level).
- **An extension name Cocos also has** (input-system's `Input` and `Touch`, profiler's `Profiler`, advanced-inspector's `[ReadOnly]`) is ambiguous where both namespaces are used (CS0104). The fix is the usual C# one, and the error message says it:
  - write it in full: `Ext.InputSystem.Input.getKeyDown(...)`;
  - or alias the type at the top of the file: `using Input = Ext.InputSystem.Input;`. An alias wins over a `using` namespace, global ones included, so `Input` is then input-system's and `cc.Input` stays Cocos';
  - or alias the namespace: `using IS = Ext.InputSystem;` then `IS.Input`, `[AI.ReadOnly]`.
- **A missing using** is named in the error: "It is in Ext.FxTween: add `using Ext.FxTween;`", or "add `using static Ext.FxTween.Exports;`" for a function.
- **Fallbacks**, listed in the report:
  - Two files of the project export the same name: both move to their folder's namespace below `Project`: `Project.Scripts.Ui.Button`, `Project.Scripts.Game.Button`. Functions go into a class named after the file: `Project.Scripts.TsLib.HealthExports.lerp(...)`.
  - A project function named like a Cocos one (`lerp`): both would be `using static`, so it moves the same way.
  - Two modules of one extension: the one its `index` exports keeps `Ext.<Package>`, the other moves to its folder: `Ext.VirtualCamera.Core.ComposerSettings`.
  - A project type named `Ext`, `Project` or `ProjectExports` moves to its folder's namespace.
  - An extension exporting a type named `Exports`: its functions go into `Ext.<Package>.<Package>Exports` instead.

**Limits.**
- Only declarations are read, file by file, without running the TypeScript compiler's type checker: inferred types of unannotated values are mostly `dynamic`. Annotate exports for better C#.
- `export default` works; `export =`, namespaces and `declare module` are not bound.
- Imported bindings are read-only: `export let` variables can be read, not assigned.
- TS interop needs the `typescript` package in `extensions/csharp/node_modules` (`npm install`).

## What is saved (Unity's rule)

The C# side follows Unity's serialization rule. The API underneath stays Cocos', and the result is Cocos' `@property`.

**Classes that get `@ccclass('ClassName')` automatically:**
- every class deriving from `Component`. An abstract base component gets it too, when it declares saved fields;
- every class marked `[Serializable]` (System's), for data nested in components;
- every class used as the type of a field marked `[SerializeField]` or `[Property]`.

`[ClassName("Game.Enemy")]` sets another name. Names must be unique across the C# scripts; a duplicate is an error that names both files.

**Which fields are saved, and become `@property`:**
- **public** instance fields of a serializable type;
- **private / protected** fields with **`[SerializeField]`**. A `_name` field is also given `visible: true`, because Cocos hides fields starting with `_`;
- **`[HideInInspector]`**: saved, not shown (`visible: false`);
- **`[NonSerialized]`** (System's): never saved;
- static, `const` and `readonly` fields are never saved;
- public fields of other types (`Dictionary`, delegates, interfaces, classes that aren't `[Serializable]`…) stay plain fields, silently, as in Unity;
- properties (`get`/`set`) are saved only with an explicit `[Property]`.

The serializable types, and what each becomes:

| C# field type | Decorator | Default without an initializer |
|---|---|---|
| `double` / `float` | `@property` | `0` |
| `int` and other integers | `@property(CCInteger)` | `0` |
| `bool` | `@property` | `false` |
| `string` | `@property` | `''` |
| an enum (yours or Cocos') | `@property({ type: Enum(E) })` | the 0 value |
| `Vec2`, `Vec3`, `Vec4`, `Color`, `Size`, `Rect`, `Quat`, `Mat4`… | `@property(Vec3)`… | `new Vec3()` |
| `Node`, any component, any asset (`Prefab`, `SpriteFrame`, `AudioClip`…) | `@property(Node)`… | `null` |
| a `[Serializable]` class | `@property(ItemStack)` | `null` |
| arrays and `List<T>` of the above | `@property([Node])`, `[CCInteger]`, `[CCFloat]`, `[CCString]`, `[ItemStack]`… | `[]` |

**Field attributes** (several combine, `[Tooltip("…"), Range(0, 1)]`):

| C# | Cocos option |
|---|---|
| `[Tooltip("…")]` | `tooltip` |
| `[Range(min, max)]`, `[Range(min, max, step)]` | `range` |
| `[Min(x)]`, `[Max(x)]`, `[Step(x)]` | `min`, `max`, `step` |
| `[Slide]` | `slide: true` (a slider, with `Range`) |
| `[DisplayName("…")]`, `[DisplayOrder(n)]` | `displayName`, `displayOrder` |
| `[Multiline]` | `multiline: true` |
| `[Group("Tab")]` | `group` (Cocos property groups) |
| `[ReadOnly]` | `readonly: true` |
| `[Type(typeof(Sprite))]` | `type` (overrides the field type) |
| `[FormerlySerializedAs("old")]` | `formerlySerializedAs` (keeps data saved under the old name) |
| `[HideInInspector]`, `[Visible(true/false)]` | `visible` |
| `[EditorOnly]`, `[Unit("m")]`, `[Radian]`, `[Animatable(false)]`, `[OverrideProperty]` | `editorOnly`, `unit`, `radian`, `animatable`, `override` |
| `[Property(Type = typeof(X), Serializable = false, …)]` | `@property({...})`, every option, for accessors and special cases |

An Inspector attribute on a field that isn't saved, or `[SerializeField]` on a type Cocos can't save (a `Dictionary`…), is a warning with file and line.

**Class attributes:**

| C# | Cocos |
|---|---|
| `[Menu("Path/Name")]` | `@menu` (Add Component menu) |
| `[ExecuteInEditMode]` | `@executeInEditMode` |
| `[RequireComponent(typeof(Sprite))]` | `@requireComponent(Sprite)`; several allowed |
| `[ExecutionOrder(-10)]` | `@executionOrder(-10)` |
| `[DisallowMultiple]` | `@disallowMultiple` |
| `[PlayOnFocus]` | `@playOnFocus` |
| `[Help("url")]`, `[Icon("url")]`, `[Inspector("url")]` | `@help`, `@icon`, `@inspector` |
| `[UniquelyReferenced]` | `@uniquelyReferenced` |
| `[ClassName("Name")]` | the name in `@ccclass('Name')` |

**Renaming classes.**
- **Component classes are safe to rename:** a scene stores a component under its script's uuid (its `__type__` is the compressed uuid of the `.ts`), not under the class name. Rename the `.cs` in Creator so the `.ts` keeps its uuid.
- **Nested `[Serializable]` classes are saved under their ccclass name.** Keep `[ClassName("OldName")]` when renaming one, or the saved data won't load.

**A property (`get`/`set`) in the Inspector** needs `[Property]`, since only fields are saved automatically:

```csharp
private int _level = 1;

[Property]
public int Level
{
    get => _level;
    set { _level = value; log($"level {value}"); }
}
```

**The old lowercase attributes still work:** `[ccclass]`, `[property]`, `[menu]`, `[requireComponent]`, `[tooltip]`, `[range]`, `[type]`, `[serializable]`… The Console only notes that `[ccclass]`, and `[property]` on a public field, are no longer needed.


## Supported C#

- Classes, single inheritance, abstract classes, static classes, nested classes (flattened to `Outer_Inner`).
- Interfaces, enums, generics (with `where T : Class` constraints), delegate types.
- Fields, `const`, `readonly`, auto properties, properties with accessors, static members, static constructors.
- One constructor per class, with `base(...)`.
- Methods with optional and `params` parameters. Overloads are renamed `name_2`, `name_3`... because TypeScript has no overloads.
- Lambdas, local functions, method groups as callbacks (bound to `this`, with a stable identity).
- `Action` / `Func`, and events with `+=` / `-=` (multicast, like C#).
- `if`, loops, `foreach` (over arrays, `List`, `Dictionary` with `kv.Key` / `kv.Value` or `var (k, v)`, and `HashSet`), `switch` (constants, patterns, `when`), switch expressions.
- `is` / `as`, type and declaration patterns, `var` / relational / `and` / `or` / `not` / property patterns, `?.`, `??`, `??=`, `nameof`, `typeof(T)`, `default`.
- String interpolation, with `:F2` / `:N1` / `:0.00` / `:D3` formats.
- `try` / `catch` (a catch by your own exception class uses `instanceof`) / `finally`, `throw`, `throw;`.
- `async` / `await` with `Task` and `Task<T>`, which become `Promise`. Also `Task.Delay`, `Task.WhenAll` / `WhenAny`, `Task.FromResult`, and `TaskCompletionSource<T>` to wrap callback APIs.
- Iterators: `yield return` / `yield break` in methods, getters and local functions returning `IEnumerator`, `IEnumerator<T>`, `IEnumerable` or `IEnumerable<T>`. See [Coroutines and iterators](#coroutines-and-iterators-yield).
- **Integer semantics:** `int / int` truncates (`Math.trunc`), and so does `(int)x` from a floating-point value.
- **Collections:**
  - `List<T>` and arrays become JavaScript arrays: `Count`, `Add`, `AddRange`, `Insert`, `Remove`, `RemoveAt`, `RemoveAll`, `Contains`, `IndexOf`, `Find`, `FindAll`, `Exists`, `Sort` (numbers sort by value), `ToArray`, `GetRange`...
  - `Dictionary<K,V>` becomes `Map`: indexer, `Add`, `ContainsKey`, `TryGetValue(k, out var v)`, `Remove`, `Keys`, `Values`, `GetValueOrDefault`...
  - `HashSet<T>` becomes `Set`.
- **LINQ (method syntax, eager, on arrays and lists):** `Select`, `Where`, `Any`, `All`, `Count`, `First(OrDefault)`, `Last(OrDefault)`, `Sum`, `Average`, `Min`, `Max`, `OrderBy(Descending)`, `ToList`, `ToArray`, `Distinct`, `Take`, `Skip`, `Reverse`, `Concat`, `ToDictionary`, `SelectMany`.
- **Strings:** `Length`, `Substring`, `IndexOf`, `Contains`, `StartsWith`, `EndsWith`, `ToUpper`, `ToLower`, `Trim`, `Split`, `Replace`, `PadLeft`, `PadRight`, `string.Join`, `string.IsNullOrEmpty` / `IsNullOrWhiteSpace`, `string.Format`.
- **Numbers and output:** `int.Parse` / `TryParse`, `float` / `double.Parse` / `TryParse`, `ToString("F2")`, `Math` and `MathF` (including `Clamp`), `Console.WriteLine` and `Debug.WriteLine`, which become `console.log`.

The few helpers this needs live in `assets/cs-runtime.ts` (`db://csharp/cs-runtime`), which generated files import.

### Coroutines and iterators (yield)

An `IEnumerator` method is a TypeScript generator: `yield return x;` is `yield x;`, `yield break;` is `return;`. It runs one step each time something calls `next()` on it, which is what a coroutine runner does. With the unity-style extension, its `StartCoroutine` takes the C# `IEnumerator`:

```csharp
using System.Collections;
using cc;
using static cc.Globals;
using Ext.UnityStyle;

public class Blinker : MonoBehaviour
{
    [SerializeField] private double interval = 0.5;   // csharp's own attribute
    [Header("Look")] public Node target;              // unity-style's

    void Start() => StartCoroutine(Blink(3));        // a Unity message: no CSX2010 under MonoBehaviour

    IEnumerator Blink(int times)
    {
        for (var i = 0; i < times; i++)
        {
            target.active = !target.active;
            yield return new WaitForSeconds(interval);
        }
        yield return null;                              // the next frame
        yield return Fade();                            // runs inside this one
        yield return StartCoroutine(Fade());            // waits for another coroutine
        if (times == 0) yield break;
        log("done");
    }

    IEnumerator Fade() { yield return new WaitUntil(() => target.active); }
}
```

becomes

```ts
    private Start(): void {
        this.StartCoroutine(this.Blink(3));
    }
    private *Blink(times: number): Iterator<any> {
        for (let i = 0; i < times; i++) {
            this.target.active = !this.target.active;
            yield new WaitForSeconds(this.interval);
        }
        yield null;
        yield this.Fade();
        yield this.StartCoroutine(this.Fade());
        if (times === 0) {
            return;
        }
        log('done');
    }
```

- **What the yielded values mean** is the runner's business. unity-style's: `null` is the next frame, a `WaitForSeconds` / `WaitUntil`... waits, a `Coroutine` (what `StartCoroutine` returns) waits for that one, another iterator runs nested, a `Task` (a Promise) waits until it settles. `StopCoroutine` and `StopAllCoroutines` work with what `StartCoroutine` returned, the iterator, or the method name (`StartCoroutine("Blink", 3)`).
- **Types.** `IEnumerator` is `Iterator<any>`, `IEnumerator<T>` is `Iterator<T>`. TypeScript generators, `Iterator` and iterator-shaped types of the TS interop are `IEnumerator` in C#, so the two mix both ways.
- **`IEnumerable` / `IEnumerable<T>` iterators run to their end when called** and return an array of what they yielded: `IEnumerable<T>` is an array in the generated code (`foreach`, LINQ, `Count`...), so it stays one. `yield break` returns the array so far. Use `IEnumerator` for lazy or endless sequences.
- **By hand:** `while (e.MoveNext()) use(e.Current);` and `e.Dispose()` (which runs the iterator's `finally` blocks) work on an `IEnumerator`.
- **Local functions and getters** can be iterators. Since they are arrows / accessors in the generated code, an `IEnumerator` one returns a generator function called with `this` (`return (function* (this: any) { ... }).call(this);`).
- **Not a lifecycle method:** `IEnumerator Start()` (or `start`, `Update`...) is called as a message, which ignores what it returns, so its code never runs (warning CSX2012). Write `void Start() { StartCoroutine(Run()); }`.
- Lambdas can't be iterators (C# rule); `async` iterators (`IAsyncEnumerable`) are not supported.
- **Builds:** Cocos compiles web builds to ES5 with Babel, which turns generators into its `regeneratorRuntime` helper; unity-style checked that it ships and runs. The generated code has no spread or rest syntax, and `foreach` only iterates arrays.

## Not supported, and limits

Each of these is reported as a C# error with file and line; nothing is silently dropped:
- `struct`, `record`, tuples, ranges and indexes (`^1`), indexers, user-defined operators, finalizers.
- More than one constructor, or `this(...)` chaining.
- `ref` / `out` parameters. The exceptions are `Dictionary.TryGetValue` and `TryParse`.
- `async` iterators, LINQ query syntax, `goto`, `lock`, `using`, `unsafe`.
- Partial classes split over several files, default interface methods, `is IInterface` (interfaces don't exist at runtime).

Also note:
- **Numbers:** there is one number type at runtime. `x is int` and `x is double` both mean "is a number", integer overflow does not wrap, and `long` is exact only up to 2^53. `Math.Round` rounds .5 up, where C# rounds to even.
- **`char` is a one-character string.** Use `(int)c` and `(char)n` for codes. Char arithmetic gets a warning.
- **Exceptions:** all .NET exceptions become `Error`, and catching `ArgumentException` catches any error.
- **One Component per file**, as Cocos requires. Keep the file and class names equal.
- **Don't edit the generated `.ts`:** it is overwritten. A `.ts` you wrote yourself, without the header, is never overwritten; there is an error instead.
- **Rename or move scripts in Creator,** in the Assets panel or the Project browser. The generated `.ts` is moved too, so scenes keep their components. Moving files outside Creator gives the `.ts` a new uuid.
- **`CocosGame.csproj`, `obj/` and `bin/`** at the project root exist for the IDE only; you can ignore them in version control.

## How it works

- **The transpiler** (`tool/CsTranspiler`, .NET 9, Roslyn):
  - It compiles every `.cs` under `assets/` against the bindings, then emits TypeScript using the semantic model. Calls bind to the right overload, integer division is known, methods used as values are known.
  - It runs as a server: one JSON request per line on stdin, one answer per line on stdout. The only commands are `compile`, `usings`, `ping` and `exit`, and no code is evaluated. A recompile reuses the files that didn't change: about 60 ms for the samples, against 1.2 s cold.
  - It writes a `.ts` only when its text changes.
- **The bindings** (`tool/Cocos.Bindings`):
  - `Cocos.g.cs` is generated from `cc.d.ts` by `source/bindings/generate.ts`, which uses the TypeScript compiler API. `Lang.cs` adds the decorator attributes and the vector operators.
  - Coverage for Creator 3.8.6: 976 classes, 509 interfaces, 298 enums, 267 module functions, 318 module variables and 15,603 members are bound. 2 members are skipped; see `bindings-report.txt`.
  - **How TypeScript maps to C#:**
    - Names stay as in TypeScript. Where a C# name must change, `[TsName]` records the original.
    - `number` → `double`, `any` → `dynamic`. Unions in parameters become overloads.
    - Callbacks become `Action` / `Func`. `callback: any` becomes `System.Delegate`.
    - `Constructor<T>` becomes `System.Type`, plus a generic overload without that argument (`getComponent<T>()`).
  - **How TypeScript declarations become C# types:**
    - String enums become classes of string constants.
    - Cocos mixins such as `EventTarget` become real classes.
    - `export import Vec3 = math.Vec3` makes `Vec3` a `cc` type.
    - Classes implement the "like" interfaces (`IVec3Like`...) they match structurally.
- **TS interop** (`source/bindings/ts-interop.ts`):
  - It reads the exported declarations of the project's and extensions' `.ts` files with the TypeScript parser and writes declaration-only C# stubs to `temp/csharp/TsBindings.g.cs`. Each declaration carries `[TsModule("db://assets/Scripts/Health")]`.
  - The transpiler compiles the stubs with the scripts; using a stub's type or function emits the import: a relative path for `db://assets`, the `db://<extension>/...` specifier for extensions. Errors inside the stubs are only warnings, so a TypeScript oddity never blocks the C#.
  - Decorators are found statically: the shape of what an exported function or constant is or returns (following type aliases, overloads and the module's own helper functions), whether its code calls cc `property(...)`, and whether it pushes to a list. Each becomes an attribute class marked `[TsDecorator(...)]`, which tells the transpiler how to write the call. Decorators duplicating csharp's own attributes are left out (see above), and classes with the `@unityMessages` JSDoc tag get `[TsUnityMessages]`.
  - It runs in a worker thread, so the editor does not pause while it reads the TypeScript.
- **The editor side** (`source/main.ts`):
  - It watches `.cs` files, sends compiles to the server and refreshes the written `.ts` assets.
  - It watches hand-written `.ts` files and keeps the TS interop stubs current.
  - It moves and deletes generated scripts with their `.cs` through asset-db, which keeps uuids.
  - It writes the IDE project (which includes the stubs).

## Development

```bash
npm install
npm run build        # tsc + esbuild -> dist/
npm run build:tool   # dotnet build -> tool/bin (the extension also does it when needed)
npm run bindings     # regenerate tool/Cocos.Bindings/Cocos.g.cs from cc.d.ts
npm test             # unit tests + samples: Roslyn errors, golden TypeScript, tsc against cc.d.ts with Cocos' settings, error reporting, server protocol
node scripts/ts-interop.js [project] [--out dir] [--exclude glob] [--no-global]   # TS interop stubs of a project, from the command line
```

The samples include hand-written TypeScript (`samples/assets/Scripts/TsLib`) and a fixture extension runtime (`samples/extensions/fx-tween`, mounted as `db://fx-tween`) for the TS interop. For the decorators, `samples/extensions/advanced-inspector` and `samples/extensions/cocos-playground` hold byte-identical copies of `AdvancedInspector.ts` and `PlayGroundField.ts` (the test checks them against the originals when those exist); `Banner.cs` and `InspectorDemo.cs` use them. `samples/extensions/unity-lite` holds byte-identical copies of unity-style's `core/coroutines.ts` and `engine/decorators.ts` with a reduced `MonoBehaviour` (`@unityMessages`); `Coroutines.cs` uses it, and the test runs its generated coroutines in node with unity-style's own scheduler, checks that unity-lite's duplicates of csharp's attributes are left out, and that its Unity messages get no CSX2010. Inside CocosGoat, a C# `MonoBehaviour` of the real unity-style (`tests/interop/UnityUse.cs`) is compiled and type-checked against its sources. The test type-checks the generated TypeScript with those sources, and runs cocos-playground's own scanner (`source/analysis/scanDecorators.ts`) on it. Inside CocosGoat, `npm test` also checks a C# script using the real tween-pro runtime (`tests/interop/TweenUse.cs`). Set `CS_TOOL=<path to CsTranspiler.dll>` to test a build other than `tool/bin`, which is locked while Creator runs the transpiler.

`UPDATE_GOLDEN=1 npm test` rewrites the golden files in `tests/golden`.
